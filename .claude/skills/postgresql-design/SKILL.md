# PostgreSQL design

## Purpose

Schemas that protect data integrity with constraints, serve the service's real queries
efficiently, and stay strictly owned by one service.

## When to use

- New tables or columns; new query paths; slow queries.
- Reviewing persistence adapters or migrations.

## Prerequisites

- Service `CLAUDE.md` (database name `<name>_db`), `database-migrations`,
  `transaction-management`.
- Local PostgreSQL 16 via Compose or Testcontainers.

## Concepts and architecture

**Ownership**

| Object | Rule |
|---|---|
| Database | `<name>_db`, one per service (`docs/architecture/service-catalog.md`). |
| Roles | `<name>_service` (app: DML only), `<name>_migrator` (DDL, used by Flyway/migrate), `<name>_cdc` (REPLICATION, SELECT on `outbox`). |
| Schema | `public` inside the service database is fine; no cross-database references, no `dblink`/`postgres_fdw`. |

Created in `infrastructure/postgres/init/<name>.sql` (owned by `database-engineer`).

**Types**

| Concept | Type |
|---|---|
| IDs | `uuid` (generated by the application, v7 preferred for index locality) |
| Money | `bigint` minor units + `char(3)` currency |
| Timestamps | `timestamptz`, always UTC from the app |
| Status | `text` + `CHECK (status IN (...))` (easier to evolve than enums) |
| Flexible attributes | `jsonb` only for genuinely schemaless data (product attributes), with GIN index if queried |
| Optimistic lock | `version bigint NOT NULL DEFAULT 0` |

**Indexes**

- B-tree composite: put equality columns first, then range/sort column.
- Partial index for hot subsets: `WHERE status = 'PENDING'`.
- Covering index with `INCLUDE` to enable index-only scans.
- Every foreign key column (within the service) gets an index.
- GIN for `jsonb` containment / full-text.

## Step-by-step workflow

1. List the aggregate's invariants and the queries the service will run (with filters,
   sort order and expected cardinality).
2. Map aggregates to tables (one root table, child tables for collections).
3. Express invariants as constraints: `NOT NULL`, `CHECK`, `UNIQUE`, FKs (inside the
   service only).
4. Design indexes per query; avoid speculative indexes.
5. Write the migration (`database-migrations`).
6. Load realistic data volumes locally and check plans with `EXPLAIN (ANALYZE, BUFFERS)`.

## Practical code examples

Order tables (order_db):

```sql
CREATE TABLE customer_order (
  id              uuid PRIMARY KEY,
  customer_id     uuid        NOT NULL,
  status          text        NOT NULL CHECK (status IN ('PENDING','INVENTORY_RESERVED','PAYMENT_AUTHORIZED','CONFIRMED','REJECTED','CANCELLED')),
  total_minor     bigint      NOT NULL CHECK (total_minor >= 0),
  currency        char(3)     NOT NULL,
  placed_at       timestamptz NOT NULL,
  version         bigint      NOT NULL DEFAULT 0
);

CREATE TABLE order_line (
  order_id        uuid    NOT NULL REFERENCES customer_order(id) ON DELETE CASCADE,
  line_no         int     NOT NULL,
  sku             text    NOT NULL,
  quantity        int     NOT NULL CHECK (quantity > 0),
  unit_price_minor bigint NOT NULL CHECK (unit_price_minor >= 0),
  PRIMARY KEY (order_id, line_no)
);

-- "my orders, newest first" with keyset pagination
CREATE INDEX customer_order_customer_placed_idx
  ON customer_order (customer_id, placed_at DESC, id DESC) INCLUDE (status, total_minor, currency);

-- saga timeout scanner only looks at in-flight orders
CREATE INDEX customer_order_inflight_idx
  ON customer_order (placed_at) WHERE status IN ('PENDING','INVENTORY_RESERVED','PAYMENT_AUTHORIZED');
```

Keyset pagination query:

```sql
SELECT id, status, total_minor, currency, placed_at
FROM customer_order
WHERE customer_id = $1
  AND (placed_at, id) < ($2, $3)        -- cursor from the last row of the previous page
ORDER BY placed_at DESC, id DESC
LIMIT 50;
```

Reading a plan:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status, total_minor, currency, placed_at FROM customer_order
WHERE customer_id = '0190d1c4-...' ORDER BY placed_at DESC, id DESC LIMIT 50;
-- Expect: Index Only Scan using customer_order_customer_placed_idx ... Heap Fetches: 0
-- Red flags: Seq Scan on large table, Sort node with external merge, rows estimate off by >10x
```

Role setup (`infrastructure/postgres/init/order.sql`):

```sql
CREATE ROLE order_migrator LOGIN PASSWORD :'order_migrator_password';
CREATE ROLE order_service  LOGIN PASSWORD :'order_service_password';
CREATE DATABASE order_db OWNER order_migrator;
\connect order_db
ALTER DEFAULT PRIVILEGES FOR ROLE order_migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO order_service;
REVOKE CONNECT ON DATABASE order_db FROM PUBLIC;
GRANT CONNECT ON DATABASE order_db TO order_service;
```

## Recommended project structure

```text
infrastructure/postgres/init/<name>.sql                  database, roles, publication
services/<kotlin-svc>/src/main/resources/db/migration/   Flyway scripts
services/<go-svc>/migrations/                            golang-migrate scripts
```

## Best practices

- Constraints in the database, invariants in the domain — both.
- Name constraints and indexes explicitly (`<table>_<cols>_idx`, `<table>_<rule>_chk`).
- Keyset pagination over `OFFSET` for user-facing lists.
- Keep transactions short; no user think-time inside a transaction.
- Monitor with `pg_stat_statements` in every environment.
- `REVOKE CONNECT ... FROM PUBLIC` so other services' roles cannot connect.

## Anti-patterns

- Another service connecting "just to read" — publish an event or expose an API.
- `float`/`double` for money.
- `timestamp without time zone`.
- Indexing every column; duplicated left-prefix indexes.
- Native `ENUM` types that need `ALTER TYPE` for every new status.
- Using the migrator role for the application.

## Failure scenarios

| Scenario | Symptom | Handling |
|---|---|---|
| Missing index on hot path | Seq scans, CPU spikes | Add index concurrently (`database-migrations`). |
| Stale statistics | Bad plans after bulk load | `ANALYZE <table>`; tune autovacuum per table. |
| Table bloat on outbox | Growing table, slow vacuum | Delete captured rows promptly; aggressive autovacuum on `outbox`. |
| Hot row contention | Lock waits on one stock row | Conditional atomic updates, shorter transactions (`transaction-management`). |

## Testing strategy

- Repository integration tests with Testcontainers PostgreSQL (real constraints).
- Constraint tests: inserting invalid data fails with the expected SQLSTATE (`23514`,
  `23505`).
- Plan checks for critical queries on seeded data (assert index usage in a test or in a
  documented `EXPLAIN` in the PR).

## Definition of Done

- Tables owned by exactly one service; no cross-database references.
- Invariants backed by constraints; types follow the table above.
- Each query path has a justified index; plan checked on realistic data.
- Roles separate migrator and application privileges.
